5. Adaptive learning: how to make it actually work
This is one of the most important parts of the whole project.

Do not begin by fine-tuning a model. Build a persistent learning system first.

Every investigation should store:
- Target and program scope.
- Endpoint and HTTP method.
- Authentication context and role.
- Vulnerability hypothesis.
- Test performed.
- Sanitized request and response evidence.
- Result: confirmed, rejected, inconclusive or duplicate.
- Reason for the result.
- Model and prompt version.
- Researcher review and final report outcome, if available.
Then use those records to improve future research.
Adaptive research loop
1. Observe
   
   Discover an endpoint, API parameter or application behavior.
2. Understand
   
   Retrieve relevant application context and security knowledge.
3. Hypothesize
   
   Generate a specific vulnerability hypothesis with supporting evidence.
4. Investigate
   
   Run a bounded, authorized test.
5. Evaluate
   
   Compare expected and actual behavior; reject weak hypotheses.
6. Learn
   
   Store the outcome and update future hypothesis prioritization.

For example, if your system repeatedly finds that a certain endpoint pattern is harmless, it can reduce the priority of similar hypotheses. If a particular API pattern has led to verified authorization issues, it can prioritize examining similar patterns in future applications.

That is adaptive learning without pretending the model has updated its own weights.

Later, once you have a meaningful dataset of reviewed examples, you can consider fine-tuning.

1. What a 50-agent system should actually look like
The key is that 50 agents should not mean 50 independent bots randomly scanning websites.

It should mean a coordinated team of specialist workers, all sharing application knowledge, security intelligence, findings and investigation history.

I'd design it like this:
Central Research Orchestrator
Schedules work, assigns agents, manages state, budgets and priorities

Discovery Team
Subdomain, asset, crawling, JavaScript, API and schema workers

Application Analysis Team
Authentication, roles, API behavior, objects and workflows

Vulnerability Research Team
Authorization, injection, SSRF, business logic and other focused researchers

Verification Team
Reproduction, false-positive rejection, deduplication and impact analysis



Shared Research Memory
Application graph · CVE index · Disclosed reports · Prior tests · Evidence · Outcomes

Controlled Investigation Engine
Scope validation · Request budgets · Test accounts · Burp integration · Approval gates

Verified Findings → Human Review → HackerOne Report


The orchestrator assigns tasks dynamically. One endpoint might need five agents investigating different questions; another might need only one. Workers should not duplicate work unnecessarily.

A useful distinction: these are logical worker slots. They don't have to be 50 separate model instances. Workers can share model providers, run asynchronously, and use ordinary code for deterministic tasks.

I would start with 8–12 logical agents and a smaller number of concurrent investigations. Increase concurrency only when the evidence shows that it improves results without creating excessive noise or target load.
3. The CVE search index is a major part of that idea
I would build a dedicated Security Intelligence Engine rather than simply giving agents access to a folder of CVE files.

It should ingest:
- CVE records and vendor advisories.
- CWE weakness descriptions.
- CAPEC attack patterns.
- Security bulletins and patch notes.
- Publicly disclosed vulnerability reports.
- Your own verified and rejected investigation history.
The search process should understand context.

For example, suppose Bounty Hunter discovers a Laravel application using a particular package version. The intelligence engine should retrieve relevant vulnerabilities and advisories, check whether their affected versions match, and give the researcher useful context.

It should not simply see the word "Laravel" in a CVE description and declare the application vulnerable.

The index should support semantic search, exact keyword search, version matching, dates and source provenance.
4. The model: QLoRA GLM 5.2 versus hosted models
The post's QLoRA approach is interesting, but I would not copy that part first.

There are three separate capabilities here:
Capability	What it does
RAG and research memory	Retrieves relevant findings and security knowledge
Feedback and evaluation	Learns which investigation strategies produce useful results
Fine-tuning / QLoRA	Adapts model behavior using a curated training dataset

You can build the first two without training your own model.

For your first implementation, use hosted model APIs through a provider-independent gateway. That lets Antigravity or OpenCode drive the development workflow without requiring you to run a local model.

Once Bounty Hunter has enough reviewed investigation records, you can evaluate whether fine-tuning improves performance on a fixed benchmark. Fine-tuning without good training examples could actually make the system worse.
5. The most important part: continuous research
This is the part I would specifically take from the post.

I would implement a scheduler that keeps the system working through a queue of authorized research tasks.

For an in-scope program, the process could be:
1. Check for permitted scope or asset changes.
2. Discover newly available application surfaces.
3. Map new routes, APIs and application behavior.
4. Retrieve relevant security intelligence.
5. Generate ranked, evidence-based vulnerability hypotheses.
6. Assign investigation tasks to specialist workers.
7. Execute controlled tests within program rules and request budgets.
8. Send promising candidates to independent verification.
9. Store results, including rejected hypotheses.
10. Prioritize the remaining research tasks.
This gives you continuous research without indiscriminately attacking production systems. Each program's scope, rate limits, exclusions and testing rules must be enforced for every worker. Destructive tests, access to other users' private information and state-changing actions need appropriate safeguards and approval.

My conclusion
I would use that kid's system as the ambition, not as a proven technical specification to copy.

The difference between the system you have and the system you want isn't just the number of agents. It's the ability to maintain a persistent understanding of an application and conduct many coordinated, evidence-driven investigations over time.

My proposed target for Bounty Hunter is:

An always-running, multi-agent security research harness with a CVE intelligence index, shared application memory, adaptive investigation, Burp integration and independent vulnerability verification.


The goal is not to produce thousands of URLs or run 50 agents just to say 50 agents are running. The goal is to produce fewer, stronger, reproducible findings.




The core modules to implement
Module A — Program and scope manager
This is the first thing that happens when someone gives Bounty Hunter a target.

Example:
bounty-hunter program add
bounty-hunter program validate --program example
bounty-hunter research start --program example


Store a program profile containing:
Field	Example
Program name	Example SaaS
In-scope assets	Explicit approved domains and IPs
Out-of-scope assets	Excluded domains, paths and systems
Allowed test categories	As specified by program
Rate limits	Program-defined request limits
Authentication	Researcher-owned test accounts
Restrictions	Prohibited test types and actions
Validity	Scope review and expiry information

The scope engine should enforce:
- Exact host and asset matching, including subdomain rules.
- Redirect validation at every hop.
- DNS resolution and destination validation.
- Request and concurrency budgets.
- Per-program and per-host rate limits.
- Explicit restrictions on destructive and state-changing operations.
- A kill switch for an individual program or the entire system.
Do not let an agent interpret a wildcard as permission to test unrelated infrastructure. The program's actual policy is authoritative.
Module B — Discovery engine
Keep the useful recon capabilities you already built. The difference is that every discovery result should become a structured record rather than a line in a text file.

It should discover:
Area	Expected output
Hosts	In-scope subdomains and discovered services
Web applications	Live applications and technologies
Routes	Pages and application paths
JavaScript	Bundles, route references and API references
APIs	REST, GraphQL and other observed interfaces
Parameters	Query, path, body and header parameters
Documentation	OpenAPI and other published API schemas
Traffic	Imported HAR and Burp observations

Tools such as subfinder, httpx, katana and nuclei can remain as adapters where useful. Don't let each tool create its own independent data format.

Every result should feed the same data model.
Module C — Application knowledge graph
This is one of the most important new capabilities.

A URL list tells you where an application might be. It does not tell you how the application works.

The knowledge graph should connect:
- Applications to routes.
- Routes to API endpoints.
- Endpoints to parameters.
- Endpoints to authentication requirements.
- Users to roles and tenants.
- Resources to their owners.
- Workflows to their state transitions.
- Findings to the requests and observations that support them.
Example:
Application
  ├── Account Management
  │     ├── GET /api/accounts/{account_id}
  │     ├── PATCH /api/accounts/{account_id}
  │     └── DELETE /api/accounts/{account_id}
  │
  ├── Authentication
  │     ├── Login
  │     ├── Session Refresh
  │     └── Logout
  │
  └── Billing
        ├── GET /api/invoices/{invoice_id}
        └── POST /api/invoices/{invoice_id}/export


The graph should capture what is known, what is inferred and what remains unknown. An endpoint extracted from JavaScript is not proof that the endpoint is accessible or vulnerable.
Module D — Investigation engine
This is where the project stops being a recon tool.

Build separate investigation packs. Each pack needs its own rules, preconditions, safe test methods, expected evidence and stop conditions.
Investigation pack	Main purpose
Object authorization	Check whether users can access resources they do not own
Function authorization	Check whether permissions are enforced for restricted functions
Property authorization	Check whether users can read or modify protected fields
Authentication	Examine session and identity boundaries
Business logic	Investigate workflow and state-transition weaknesses
Injection	Identify unsafe handling of untrusted input
SSRF	Assess server-side URL handling through controlled validation
Misconfiguration	Detect exposed or unsafe application configuration
Cryptography	Assess transport and sensitive-data protection
Software supply chain	Identify vulnerable components and verify affected-version applicability

These map to modern application security categories. The current OWASP Top 10 is the 2025 edition, including Broken Access Control, Security Misconfiguration, Software Supply Chain Failures, Cryptographic Failures, Injection, Insecure Design, Authentication Failures, Software or Data Integrity Failures, Logging and Alerting Failures, and Mishandling of Exceptional Conditions. 
top10.owasp.org+1


Do not treat those ten categories as equally automatable or equally likely to earn a bounty. Prioritize based on the application's actual architecture and observable behavior.

4. First build: a genuine authorization investigation
I would make the first complete automated investigation BOLA/IDOR.

Why? It gives you a practical test of whether Bounty Hunter can reason about application context rather than merely identify suspicious URLs.

Use two researcher-controlled test accounts and resources deliberately created by those accounts.
Example controlled application
Tenant A
Test account A
User A
Owns invoice A

Tenant B
Test account B
User B
Owns invoice B



The investigation
1. Capture a baseline request for an account's own test resource.
2. Replay the controlled request with the other test account's credentials.
3. Compare the outcomes while using only those accounts and resources.
4. Check whether the application enforces the intended ownership boundary.
5. Have a separate verifier repeat the finding and rule out harmless response differences.
Expected deliverable
A reproducible authorization finding supported by sanitized request/response evidence.

The system should not access unrelated customers' data to prove a vulnerability. Use test-owned data, minimal evidence and program-approved methods.

When this complete workflow works reliably in a lab, you have a meaningful first version of an actual vulnerability investigation engine.

6. Build the autonomous research loop
Your desired user experience is:
bounty-hunter research start --program example


The system should then manage the research queue by itself.

The continuous workflow:
1. Read the approved program profile.
2. Check scope validity and current restrictions.
3. Identify new or previously unanalyzed assets.
4. Discover routes, APIs and application behavior.
5. Update the application knowledge graph.
6. Retrieve relevant security intelligence.
7. Generate ranked hypotheses.
8. Assign work to the appropriate specialist agents.
9. Request only permitted tests from the execution engine.
10. Evaluate the resulting evidence.
11. Independently verify promising candidates.
12. Save confirmed and rejected results.
13. Reprioritize the remaining work.
It should schedule research intelligently rather than repeatedly scanning the entire target.
Four autonomy levels
Mode	What the system can do
Observe	Passive asset and documentation analysis.
Map	Bounded, low-noise discovery and application mapping.
Investigate	Specific controlled tests within the program's permissions.
Report	Prepare finding drafts and evidence for human review.

State-changing tests should require appropriate approval and test-account safeguards. No automated destructive testing, data exfiltration, credential attacks, or unrestricted WAF-bypass loops. Do not automatically submit reports.

11. How Bounty Hunter should prioritize research
Don't tell the AI to "find any bug." Make it rank concrete hypotheses.

Each hypothesis should have:
- A target endpoint or workflow.
- A suspected security weakness.
- The application behavior supporting the suspicion.
- What evidence is missing.
- A safe way to test it.
- Expected signals for a genuine issue.
- A stop condition.
- A likely impact, if verified.
Maintain two different scores:

Research priority — which hypothesis is worth investigating next.

Finding severity — how serious the issue is, once verified.

A suggested prioritization model:
Factor	Weight
Supporting evidence	25%
Potential impact	25%
Testability	20%
Novelty / duplicate risk	15%
Scope confidence	10%
Cost of investigation	5%

These weights are an initial heuristic, not a proven bounty-success formula. Calibrate them using the platform's own measured results.

Never let a high model confidence score turn an unverified hypothesis into a confirmed finding.

13. What proves that the platform actually finds bugs?
You need a test environment with known vulnerabilities and known secure behavior. Otherwise, you won't know whether a new agent is improving the platform or simply increasing the number of suspicious results.

Use intentionally vulnerable labs such as OWASP Juice Shop and OWASP crAPI, plus a small custom application with multiple test users, tenants, roles and workflows.

Create a benchmark with:
Metric	What it tells you
True-positive rate	How often suspected issues are genuinely present
False-positive rate	How often the system reports harmless behavior
Coverage	How many known test cases it can identify
Verification success	How many candidates survive independent reproduction
Duplicate rate	How often it repeats known findings
Time to verified result	How efficiently it investigates
Cost per verified result	Whether its agent/model use is economical
Target request volume	Whether the system stays within its operational limits

A successful first benchmark is not "found 100 vulnerabilities." It is "identified the seeded authorization flaw, rejected the clean cases, reproduced the issue, and generated a clear report."

Only after that should you test on actual HackerOne programs, and only within their explicitly authorized rules.

14. Program selection: give the platform a target-quality score
Build a program comparison tool rather than automatically selecting programs because they have wildcard scopes.

Evaluate:
Criterion	Why it matters
Scope clarity	Reduces accidental out-of-scope testing
Application complexity	Complex authorization and workflows create more research opportunities
API availability	Gives the engine structured interfaces to investigate
Authentication options	Enables legitimate multi-account testing
Program activity	Helps avoid programs with unclear or dormant processes
Scope changes	Recently added assets may deserve fresh analysis
Bounty policy	Makes potential rewards and exclusions transparent
Researcher competition	Helps estimate saturation, where reliable public data exists
Testing restrictions	Determines what the automation can safely perform

Use this score to help you choose where to spend research time. It should not claim to predict which program will pay you.

15. What I would not build yet
These features may look impressive, but they are not the foundation:
- 50 independent LLM instances.
- A custom-trained GLM or Qwen model.
- An elaborate vector database before structured data exists.
- Autonomous unrestricted fuzzing.
- A giant dashboard before the investigation engine works.
- Automatic HackerOne submissions.
- Agent-generated payload collections without an evidence-based test plan.
Build the capability to investigate first. Scale it second.
